# Namiso

[简体中文](README.zh-CN.md)

Namiso is a standalone long-term memory engine for AI agents. It keeps the raw conversation, extracts durable claims and events, links every structured memory to the messages that support it, and returns a bounded, cited context for an agent to use.

Namiso is a library, not an agent runtime. It does not plan, call tools, schedule messages, or expose an HTTP server. It owns conversation history, memory spaces, extraction, evidence, indexes, retrieval, and context assembly. You bring the agent, the model providers, and the product policy.

## Why Namiso

Most chat memory is a search box over old messages. Namiso adds a structured layer on top of that:

- Raw messages stay append-only and searchable.
- Claims and events are extracted from messages, not generated by a second model at read time.
- Every claim and event keeps evidence links, so a retrieved fact can be traced back to what was actually said.
- Current state is explicit. New facts can supersede or contradict old ones without deleting history.
- Retrieval works with both raw messages and structured memory, and returns both when useful.
- The engine is self-contained. The default providers run offline, and model providers are interfaces.

## Install

```bash
npm install @kmchai/namiso
```

Requires Node.js 24 or newer. The package is ESM and uses the built-in `node:sqlite` module. Storage is a local SQLite database. No service is required.

## Quick start

```ts
import { Namiso } from '@kmchai/namiso'

const memory = await Namiso.open({
  databasePath: './memory.db',
  memorySpace: { name: 'assistant' },
  self: {
    name: 'Aster',
    aliases: ['Ast'],
    description: 'A long-running assistant that remembers the user across sessions.',
  },
})

const conversation = memory.createConversation({ title: 'first session' })

await memory.ingest({
  conversationId: conversation.id,
  speakerId: 'user',
  role: 'user',
  content: 'I use IndexTTS2 for voice generation.',
})

await memory.drain()
await memory.consolidate()

const context = await memory.getContext({
  query: 'Which voice model do I use?',
})

console.log(context.text)
memory.close()
```

`drain()` builds conversation chunks and their indexes. It does not call the extraction model. `consolidate()` runs extraction on pending messages, one provider call per batch, and is explicit because model calls cost money and time. Call it at a session boundary, before context compaction, or on a schedule that fits the application.

## Core concepts

A **workspace** contains one or more **memory spaces**. Every read and write is scoped to one memory space.

A **conversation** is a sequence of append-only messages. Messages keep the speaker, role, content, occurrence time, and optional metadata.

Structured memory is derived from messages:

- **Entities** are people, places, objects, projects, and other things the conversation refers to. Entities can have aliases.
- **Claims** are durable facts about an entity, such as a preference, a possession, a relationship, or a plan. A claim has a status and can be superseded by a newer claim.
- **Events** are things that happened, with participants, a time, and evidence. Events support day-precision and exact timestamps when the source supports them.
- **Evidence** links a claim or event to the messages that support it.
- **Links** record relationships such as `supersedes`, `updates`, `contradicts`, `continues`, `caused_by`, `derived_from`, `related_to`, and `same_as`.

The assistant has one **self entity** per memory space. Type `self` belongs only to it. Assistant speakers resolve to this entity, and its description holds persona or background.

## Write path

1. `ingest()` appends a message and indexes it in full-text search. No model is called.
2. `drain()` processes chunk and index jobs.
3. `consolidate()` batches pending messages by conversation and sends them to the extraction provider.
4. Extraction produces entities, aliases, claims, and events. The pipeline resolves dates, links evidence, merges duplicate events when the dates and participants support it, and marks the batch consolidated.
5. Structured documents are indexed in full-text search and, when embeddings are available, in the vector index. Raw message FTS is written even if embedding fails.

A failed extraction leaves the batch pending. Call `consolidate()` again to retry. One process owns one database file. Do not open the same file for writes from two processes.

## Read path

`retrieve()` returns ranked candidates and a trace. `getContext()` runs retrieval and assembles a readable, token-budgeted context.

1. Parse the query, resolve mentioned entities, and interpret relative time.
2. Search structured memory and raw messages through SQL, full-text search, and vector channels.
3. Fuse channel rankings with Reciprocal Rank Fusion.
4. Rerank the top candidates, then apply current-state and time filters.
5. Expand linked records and evidence, bounded by the request.
6. Select evidence messages that match the query, then fill remaining slots.
7. Assemble sections against a soft token target. Excerpts are shortened before records are dropped, and `overBudget` reports when the target cannot be met.

Raw message FTS is a first-class channel. A fact can be found even when extraction never wrote it into a claim or event. `RetrieveResult.evidence` returns up to four raw message hits that can be passed into `getContext()`.

Optional retrieval features are opt-in or configurable:

- `chunkExpansion` expands chunk hits into message candidates. Default on.
- `multiHop` expands message seeds with bridge terms and can use an evidence judge. Default off.
- `salientProfile` adds a strong entity and its recent event for process or advice questions. Default off.
- `evidenceJudge` accepts a SystemOne-compatible provider for multi-hop evidence scoring.

## Public API

| Method                                                             | Purpose                                                       |
| ------------------------------------------------------------------ | ------------------------------------------------------------- |
| `Namiso.open(options)`                                             | Open a database and bind a workspace and memory space         |
| `createConversation()`, `getConversation()`, `listConversations()` | Manage conversations                                          |
| `getMessages()`                                                    | Read messages with index, time, and limit filters             |
| `ingest()`                                                         | Append one message; idempotent with `externalMessageId`       |
| `drain()`                                                          | Process chunk and index jobs                                  |
| `consolidate()`                                                    | Extract pending messages; one provider call per batch         |
| `retrieve()`                                                       | Return ranked candidates, raw evidence, and a trace           |
| `getContext()`                                                     | Return a bounded, sectioned memory context                    |
| `upcomingEvents()`                                                 | Return dated active events for plugin-level reminders         |
| `timeline()`                                                       | Return an entity's events in time order                       |
| `getEntityDetails()`, `getEventDetails()`, `getClaimDetails()`     | Read records with evidence and links                          |
| `ensureSelf()`, `ensureEntity()`                                   | Create or update the self entity or a named entity            |
| `link()`                                                           | Add a manual relation between memory records                  |
| `forget()`                                                         | Delete a message, conversation, entity, or event and clean up |
| `reindex()`                                                        | Rebuild documents, FTS rows, and vectors for the space        |
| `retryJobs()`                                                      | Retry failed jobs                                             |
| `health()`                                                         | Report counts, jobs, vector backend, providers, and warnings  |
| `close()`                                                          | Close the database                                            |

See [spec/api.md](spec/api.md) for signatures, options, and return types.

## Providers

The default stack is offline and deterministic:

| Slot       | Default                  | What it does                                        |
| ---------- | ------------------------ | --------------------------------------------------- |
| Extraction | `RuleExtractionProvider` | Pattern-based extraction for tests and small demos  |
| Embedding  | `HashEmbeddingProvider`  | Deterministic feature hashing, not a semantic model |
| Reranker   | `LexicalReranker`        | Token overlap scoring                               |

Production deployments should pass an LLM extraction provider and a real embedding model. `HttpExtractionProvider`, `HttpEmbeddingProvider`, and `HttpRerankerProvider` accept OpenAI-compatible endpoints. `SystemOneEvidenceJudge` adds an optional evidence judge for multi-hop retrieval.

```ts
import { Namiso, providersFromEnv } from '@kmchai/namiso'

const memory = await Namiso.open({
  databasePath: './memory.db',
  ...providersFromEnv(process.env),
})
```

`providersFromEnv()` reads the variables documented in [.env.example](.env.example). An endpoint URL and a model name must be set together. Embedding also needs `NAMISO_EMBEDDING_DIMENSIONS` to match the model output. Empty variables are ignored, so the offline defaults stay active.

## Configuration

| Option                               | Default                   | Notes                                                 |
| ------------------------------------ | ------------------------- | ----------------------------------------------------- |
| `databasePath`                       | required                  | Use `:memory:` for tests                              |
| `workspace.id`, `workspace.name`     | generated, `default`      | Reused by ID, or by name when ID is omitted           |
| `memorySpace.id`, `memorySpace.name` | generated, `default`      | Reused by ID, or by name within the workspace         |
| `embedding`                          | `HashEmbeddingProvider`   | Dimensions must stay stable for a database            |
| `extraction`                         | `RuleExtractionProvider`  | Use an LLM provider for production                    |
| `reranker`                           | `LexicalReranker`         | Set `rerank: false` per query to skip                 |
| `evidenceJudge`                      | unset                     | Optional judge for opt-in multi-hop evidence          |
| `salientProfile`                     | `false`                   | Add a strong entity and its recent event              |
| `chunkExpansion`                     | `true`                    | Expand chunk hits into message candidates             |
| `extractRoles`                       | `['user', 'assistant']`   | Roles sent to extraction                              |
| `knownFacts`                         | `false`                   | Send current facts to extraction for change detection |
| `self`                               | unset                     | Assistant identity: name, aliases, description        |
| `vectorIndex`                        | `auto`                    | `auto`, `sqlite-vec`, or `exact`                      |
| `chunking`                           | `{ size: 8, overlap: 2 }` | Size 1 to 64; overlap must be smaller                 |

## Design guarantees

- Raw messages are append-only. Structured memory is derived and rebuildable.
- Extraction is explicit. `ingest()` never calls the model.
- Every claim and event links to at least one evidence message.
- Current and historical claims are separate states. Replacing a fact keeps history through status and links.
- Every read and write is scoped to one memory space.
- The assistant has one self entity per space.
- Full-text search and vector indexes are derived. `reindex()` rebuilds them.
- Core code does not import an agent harness, a model SDK, or a specific vendor.
- The default providers make no network calls.

## Benchmark

The repository includes two benchmark layers:

- `bench/run.ts` reads the JSONL format from [Ornn8/chat-memory-benchmark](https://github.com/Ornn8/chat-memory-benchmark) and measures whether the evidence message for a question appears in the returned context. It does not call an answer model.
- `bench/b22` adapts the engine to benchmark-2.2, including exam and natural splits, answer generation, judging, cost accounting, and the plugin boundary. See [bench/b22/README.md](bench/b22/README.md).

```bash
# Local fixture
pnpm bench

# Public demo
node bench/run.ts --dataset ../chat-memory-benchmark/demo --out bench/out/demo

# Formal set with real providers
node bench/run.ts --dataset ../chat-memory-benchmark/datasets/natural-timegrid-20261101-v2 \
  --models --out bench/out/formal
```

Benchmark numbers depend on the dataset, provider stack, prompt, answer model, and judge. See [spec/benchmark.md](spec/benchmark.md) for recorded runs and their caveats. Do not compare an evidence-recall number with an end-to-end answer score.

## Status and limitations

Namiso is at `0.1.0`. The public API may change before `1.0`.

It is not an HTTP service, a background daemon, or a multi-process queue. One process owns one database file. It does not run an agent, schedule messages, or decide product policy. Due reminders and benchmark answer rules belong to the plugin layer.

The engine stores raw messages indefinitely unless you call `forget()`. When remote providers are configured, message content and memory context are sent to those endpoints. Keep that in mind for private or regulated data.
